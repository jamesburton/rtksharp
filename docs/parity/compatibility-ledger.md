# RtkSharp / RTK (Rust) Compatibility Ledger

Phase 0 living document. Tracks (1) which of the seven Global-Constraints
parity categories have golden fixtures and where those fixtures live, and
(2) known/accepted output differences between the Rust `rtk` binary and the
in-progress `RtkSharp` .NET port. Later phases append to both sections as
filtering behavior is actually implemented — this document does not attempt
to be exhaustive at Phase 0, since most of RtkSharp's filter modules don't
exist yet.

## Known Acceptable Differences

Populated with differences already confirmed during Phase 1/2 work. Expected
to stay short until RtkSharp implements actual filtering (Phase 4+) — not
padded with speculative entries.

| Area | Rust behavior | RtkSharp behavior | Why acceptable |
|---|---|---|---|
| Merged stdout/stderr line endings | Expected byte-exact passthrough of whatever the child process wrote (Rust's `std::process::Command::output()` returns separate, unmodified stdout/stderr byte buffers with no line-ending translation on read; the exact merge path — if any — was not located in `src/core/utils.rs`/`tee.rs` in this pass, so this is the brief's characterization rather than code-verified). | `RtkSharp/Execution/ProcessExecutor.cs`'s `AppendMergedLine` (confirmed at the current `port/dotnet-phase0` HEAD) builds the merged buffer via `StringBuilder.AppendLine(line)` on each `OutputDataReceived`/`ErrorDataReceived` callback, which appends `Environment.NewLine` (`\r\n` on Windows) regardless of the child's original line-ending bytes. | Line-ending normalization in the merged-capture path is a deliberate, low-risk simplification of .NET's event-based `OutputDataReceived` API (which already strips the original terminator per line); it does not affect any filter logic that operates on already-split lines, and is expected to be revisited only if a future filter needs byte-exact merged output. |
| Fixture file line endings (git normalization) | N/A — this is a fixture-storage concern, not a Rust-vs-RtkSharp behavior difference. | N/A | `tests/parity/fixtures/**/*.txt` and `.json` files were captured on Windows (CRLF) and may be subject to this repo's `.gitattributes` line-ending normalization on commit. **RESOLVED (Task 5):** `RewriteParityTests.cs` normalizes CRLF/LF (`Normalize()`) before byte-comparing stdout. The placeholder self-comparison note below (original `ParityRunner.CompareAsync`) is superseded for the rewrite gate, which drives the real RtkSharp binary. |
| `rtk rewrite` permission verdict / exit code (host allow-list) | Oracle loads the developer's `~/.claude/settings.json`. Its `Bash(git:*)` allow-rule makes `check_command` return `Allow`, so `rtk rewrite "git status"` / `"git log"` exit **0** (auto-allow). | RtkSharp implements no config system (out of scope per Task 4 / `RewriteCommand.cs`), so every rewritable command yields the `Ask` verdict → exit **3**. **Stdout is byte-identical** on both sides (`rtk git status` / `rtk git log`). | The delta is exit-code-only and traces entirely to config the port intentionally does not read, not to the rewrite engine. On Windows the oracle's home dir is resolved via `SHGetKnownFolderPath(FOLDERID_Profile)` (`dirs-sys` 0.4.1), which ignores `USERPROFILE`/`HOME`, so the allow-rule cannot be isolated by environment overrides, and modifying the user's real `settings.json` is out of bounds. The rewrite-parity harness (`RewriteParityTests.cs`) treats this exact pattern (oracle exit 0, RtkSharp exit 3, identical non-empty stdout) as an acceptable match; all other exit-code deltas remain hard failures. Affects exactly 2 of 26 fixture lines. Revisit if/when RtkSharp gains a config/permission system. |
| `rtk find` gitignore handling | `ignore` crate with `git_global(true)` (honors `core.excludesFile`) | Hierarchical `.gitignore` + `.git/info/exclude` only; no global excludesFile | Narrow, host-config-dependent; port targets repo-level ignore semantics; revisit if parity battery hits it. |
| `rtk grep -rln` / files-with-matches line order | Emits the file list in ripgrep's parallel directory-walker order, which is **run-to-run nondeterministic** (verified in Task 6: the *same* `target/release/rtk.exe` returned `RewriteEngine.cs, ShellLexer.cs` on 3 of 5 runs and the reverse on the other 2). | Identical: shells out to the same `rg` binary with the same flags (files-with-matches modes go through `GrepCommand`'s native passthrough), so it inherits the same nondeterministic ordering. | Line **order** in a files-with-matches listing is not part of the contract — the deterministic invariant is the *set* of matching files, which is byte-identical on both sides. `SystemParityTests.cs` treats an output pair that is equal as a sorted line multiset but unequal in index order as an ordering-only deviation (counted as matched, labelled `MATCH (rg ordering, nondeterministic)`); a missing/extra/changed line changes the multiset and still fails. Not a port bug: both sides delegate ordering to `rg`. |
| `rtk ls` / `rtk wc` exit code when coreutils are absent | Native `ls`/`wc` are spawned via the Rust `std::process::Command`; a spawn failure (binary not on PATH) surfaces as process exit **1**. | `LsCommand`/`WcCommand` shell out through `ProcessExecutor`, which maps a failed `Process.Start` (Win32Exception/"did not start") to exit **127** (the conventional "command not found" code). Filtered stdout is empty on both sides in this case. | Environment-only: manifests solely when the Unix coreutils are missing from PATH, which contradicts rtk's deployment premise (it exists to compress `ls`/`wc`/`grep` output, so those tools must be installed). `SystemParityTests.cs` prepends the Git-for-Windows `usr\bin` directory to the PATH of **both** child binaries so the filters run against real output and both exit 0; the delta is therefore not exercised. The exit-code mapping (1 vs 127) is a defensible .NET convention difference, documented here rather than "fixed" to a less-standard value. Revisit only if byte-exact spawn-failure exit parity is later required. |
| `rtk dotnet build` diagnostics on Windows-absolute paths | The text parser's `ISSUE_RE` (`src/cmds/dotnet/binlog.rs:56`) captures the file group as `[^:(]+`, which cannot cross a drive-letter colon (`C:\...`), so a Windows-absolute-path diagnostic line fails to match cleanly and the compact `Errors:`/`Warnings:` sections fall back to a `Build error #N (details omitted)` / `Build warning #N (details omitted)` placeholder. In practice this text-parser bug is masked because the Rust binary's default path injects `-bl:<tmp>` and parses the MSBuild binary log instead, which carries structured file paths and never hits this text-regex limitation. | `IssueRegex` in `DotnetCommand.cs` widens the file-capturing group to `(?:[A-Za-z]:)?[^\r\n:(]+`, an optional drive-letter prefix that lets the group cross the colon. Windows-absolute-path diagnostics now produce real `file`/`line`/`column`/`code`/`message` details instead of the placeholder; Unix/relative paths are unaffected since the prefix is optional. | Intentional, ledgered improvement (not a silent behavior drift): strictly more informative than the Rust oracle on Windows, and byte-identical to it on Unix paths. Confirmed via reviewer sign-off; covered by `DotnetCommandTests.FilterBuild_WindowsDriveLetterPath_ExtractsRealDetailsNotPlaceholder` and `ParseBuildFromText_WindowsDriveLetterPath_ExtractsRealDetails`. The underlying reason the Rust oracle avoids this bug (binlog parsing) remains deferred in RtkSharp — see the next row. |
| `rtk dotnet build` binlog `extract_binary_like_issues` salvage branch | `src/cmds/dotnet/binlog.rs:1064`'s `extract_binary_like_issues` is a salvage branch inside the deferred binary-log reader: it only fires when the parsed issue list is empty **and** the build failed **and** a binary-level error signal is present in the log, scanning the raw binlog bytes for embedded diagnostic-like strings as a last resort. | Not ported — RtkSharp's build/restore filters use the text-only path (`-bl` binlog injection itself is deferred; see the class remarks in `DotnetCommand.cs`), so there is no binary log to salvage from. | Deliberate deferral, not a gap: the salvage branch is a rare last-resort fallback for a code path (binlog reading) that is already out of scope this phase, and its trigger conditions are narrow (empty issues + failed build + binary error signal). RtkSharp's `N Error(s)`/`N Warning(s)` inline-count fallback (`ErrorCountRegex`/`WarningCountRegex` in `ParseBuildFromText`) already covers the count-visibility need for failed builds with no per-line diagnostics, so real-world impact is near-zero. Revisit only if/when binlog parsing itself is ported. |
| `rtk dotnet build`/`restore` **project count** on a multi-project, up-to-date (no-op) `*.slnx` | The oracle's default path parses the MSBuild **binary log**, which enumerates every build-graph node in the solution, so the summary reports the full count regardless of incrementality — e.g. `ok dotnet build: 4 projects, …` and `ok dotnet restore: 4 projects, …` for `RtkSharp.slnx` even when nothing rebuilt. (The binlog enumerates **4 build-graph nodes**; the `*.slnx` itself lists only **3 projects** — `RtkSharp`, `RtkSharp.Tests`, `RtkSharp.ParityTests` — the 4th node is the extra build-graph vertex MSBuild adds for the solution/restore graph. The token is `4 projects` regardless.) | RtkSharp defers binlog and counts project mentions in the console **text** via `ProjectPathRegex` (byte-identical to Rust's `PROJECT_PATH_RE` text fallback). On a no-op multi-project build the console text names only the primary/driver project, so the count under-reports: `1 projects` for `build`, `0 projects` for `restore` (restore emits no per-project text line when all are up to date). Single-project targets (`build RtkSharp.csproj`, `test RtkSharp.Tests`) are unaffected — both sides report `1 projects`. | Direct, expected consequence of the deferred binlog (see the two rows above): the *only* divergent token is the leading `N projects` integer on the summary line; error/warning counts, diagnostics, verdict icon, and exit code are byte-identical. Not a port bug — the text project-counting regex is a faithful port of Rust's own text fallback; the oracle simply has a richer source (binlog) that RtkSharp does not read this phase. `DotnetParityTests.cs` tolerates this **only** for the two multi-project `*.slnx` battery entries via a per-entry `AllowProjectCountDivergence` flag that masks the `N projects` token on both sides (`ProjectCountRegex` → `(PROJECTS)`); single-project entries do not get the allowance and match the count exactly. Not globally masked. Revisit if/when binlog parsing is ported (RtkSharp would then match the full count). |
| `rtk dotnet build` compact **`Errors:` detail line** on a FAILED build (binlog garble vs real text) | The oracle sources the compact `Errors:` section from the MSBuild **binary log** and, on a Windows-absolute-path diagnostic, garbles the location to a raw byte offset with **no filename** — observed `  CS1525(50,5) error: Invalid expression term ';'` for a `dotnet build` of a project whose real error is `Program.cs(5,17)`. (The `(50,5)` is a binlog byte offset, not a source line/column.) | RtkSharp parses the console **text** with the drive-letter-aware `IssueRegex` (see the drive-letter row above) and emits the **real** file/line/column in the compact section — `  <file>Program.cs(5,17) error CS1525: Invalid expression term ';' [<proj>]` — i.e. strictly **more informative** than the oracle. | Intentional, ledgered *improvement* (same root cause as the drive-letter row): RtkSharp is strictly better than the oracle's garbled binlog rendering on Windows-absolute paths. Error/warning **counts**, the raw `Build FAILED` diagnostic lines (byte-identical on both sides), the `fail dotnet build: … 1 errors …` verdict, and the exit code all match strictly. `DotnetParityTests.cs` tolerates only the compact `Errors:`/`Warnings:` **detail** lines on the single broken-build failure entry via a per-entry `AllowDiagnosticDetailDivergence` flag that masks those indented lines on both sides while **preserving their count** (so diagnostic-count parity is still enforced). The failing-test entry needs no such allowance — the test runs on both sides and the failure summary is byte-identical once the random TRX results path is masked. Revisit if/when binlog parsing is ported. |
